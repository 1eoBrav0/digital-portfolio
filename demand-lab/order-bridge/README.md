# Ser Order Bridge

Демонстрационный прототип переноса заказов из магазина в учётную систему. Данные вымышленные, внешние сервисы не вызываются. Python 3.11+, только стандартная библиотека.

## Проверить за минуту

Из этой папки:

```sh
python -m unittest -v
python bridge.py
```

Вход: [sample-orders.json](sample-orders.json). Выход: `result/report.json`, `result/orders.csv` и локальная `demo.sqlite`, исключённая из Git.

На чистой базе восемь событий дают три заказа на **7 020 ₽**: один повтор, четыре отклонения (конфликт ID, неизвестный товар, нехватка остатков и дробное количество). Первая доставка имитирует timeout; вторая проходит успешно. Получатель содержит ровно три заказа. В [example-result](example-result/) сохранён реальный результат первого запуска.

Повторный запуск с той же базой вернёт уже существующие корректные заказы как `duplicate`, не спишет остатки снова и не создаст повторов у получателя. Для нового независимого прогона используйте `--db fresh.sqlite --output fresh-result`, не удаляя рабочую базу.

## Что реализовано

- Нормализация порядка позиций и объединение одинаковых SKU.
- Деньги в целых копейках, цена берётся из локального справочника, не из входящего запроса.
- Транзакционная проверка и резервирование остатков; проверка параллельных запросов.
- Сохранение заказа и записи в очередь одной транзакцией.
- Постоянная очередь исходящих событий, повтор после сбоя и идемпотентный тестовый получатель.
- Проверка потери подтверждения: получатель уже сохранил заказ, отправитель повторил доставку — второй заказ не появился.

## Границы демонстрации

Это CLI-прототип, **не готовый коннектор 1С/Битрикс/n8n**, не Telegram-бот и не платёжная система. Получатель имитируется в SQLite; сетевые API, авторизация, права пользователей, отмена и возврат заказа, регулярный планировщик, backoff, мониторинг и обработка версий справочника потребуют отдельной реализации под реальное ТЗ. Два параллельных процесса доставки могут отправить событие повторно; внешний получатель тоже обязан поддерживать ключ идемпотентности.

Для реального проекта первый шаг — согласовать контракт API, сопоставление SKU, правила остатков и один тестовый заказ. Не публикуйте реальные заказы и доступы в репозитории.
